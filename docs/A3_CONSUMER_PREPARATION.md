## 4. 后续一次真实消费的最小范围

先固定消费者、安装、专属本地数据库和本轮输出目录，不使用 P/K 或 NAS 上的既有数据库。
数据库与运行文件不放进源码或安装目录。助手调用公共 CLI，原始请求、准确 ID 和响应私有保存。

| 步骤 | 公共入口 | 必须保留的事实 |
| --- | --- | --- |
| 保存核对报告 | `init`、`write` 的 create/append | 新目标拒覆盖；原请求、幂等三元组、准确 Artifact/Version、实际内容摘要与来源 |
| 精确取回 | `get` version/content_root/blob、`read-blob` | 沿准确引用读取，不用 latest；实际字节、长度及摘要一致；明确的新输出文件 |
| 实际采用 | 助手读取取回的报告并用于尚未完成的实际维护 | 哪个准确版本被使用、支撑哪项后续决定或交付；不能仅记录“哈希相同”或倒算本轮更正 |
| 原请求核对 | `operation`，必要时相同原请求 `write` | 指纹与结果一致，重放保留原 result_ref/时间，不增加版本或成功记录 |
| 结束核验 | `history`、`verify` | 真实记录和内容完整；业务采用结论与 Ledger 提交结果分开 |

本次任务拟仅保存小型文本报告，每份不超过 1 MiB；这是消费者任务限额，不修改产品 profile。
输入和回执丢失时先恢复原记录，不能用新 ID/key 猜测重建。仅查询 metadata 不证明内容完整，
必须读取实际 bytes；内容校验也不自动证明报告判断正确。

响应丢失或非零退出不能直接判定未提交。先确认原执行退出，沿原三元组查询，
再按真实提交状态继续；冲突或损坏保留原件，不覆盖历史或盲目更换身份重试。
不需要故意破坏真实库来制造故障证据，复用已有适用的接口及故障回归结果。
