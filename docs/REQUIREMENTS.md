# 需求：独立制品记录组件

状态：Candidate，A0 文档提案；Decision Authority：Owner。本文定义目标与验收要求，不构成开工批准。固定文档提交与授权以 [Gate](PROGRAM_REPOSITORY_DOCUMENTATION_GATE.md) 为准。

## 1. 问题与使用者

个人开发者、团队和其他应用需要保存数字制品的稳定身份、完整版本历史和精确内容。仅保存文件路径、文件名或模型对话，无法可靠回答“这次消费了哪个版本、内容是否完整、失败重试是否重复登记、换实现后是否仍指向原来的对象”。

目标消费者包括开发辅助程序、独立 Agent 应用和知识系统。它们消费同一组普通库/CLI 接口，但分别拥有业务判断。首阶段用独立外部进程验证公开入口；真实 Code Driver consumer 与独立 Generic Agent consumer 的采用证据属于 A3，当前两者均未完成接入。

产品价值是使长期记录不依赖某个模型、编排框架或云供应商。可视化工作流、Skill 和 Harness 可以将它作为节点使用；本仓库提供的数据边界并不代表任意厂商产品已经可以互换。

复用说明必须让外部消费者独立完成接入：按 [复用与接入指南](USAGE.md) 选择库或 CLI、准备安装与独立数据位置、保存 ID 和原幂等请求；按 [普通报告示例](REUSE_EXAMPLE.md) 串起内容写入、指定版本读回、重试核对和完整包搬运。当前示例是设计候选；A1 P5 必须以真实发行构建在隔离环境验证并补齐执行证据，不能只提供接口表作为 R08 的完成证明。

## 2. 必须满足的需求

| ID | 用户可观察行为 | 不可接受后果 |
|---|---|---|
| R01 | 新建 Artifact 后得到稳定身份；可先没有版本 | 相同字节或文件名被静默合并成同一身份 |
| R02 | 明确登记版本及父关系；保留分支及调用方提供内容的多父版本 | 原地覆盖历史、按时间自动选 current、跨 Artifact 父关系 |
| R03 | 按精确 Version/Blob 引用读取并验证内容与长度；可表达多文件内容 | 返回缺失或损坏内容却声称完整，或把逻辑键当输出路径 |
| R04 | 来源关系和外部引用随版本保存 | 内容完整性被解释为来源真实、知识有效或操作获准 |
| R05 | 原幂等身份重试返回原成功结果；冲突请求不改变状态 | 新 key 猜测重建、重复历史事件、失败中途公开半条记录 |
| R06 | 将完整、有界的可移植元数据及字节搬到另一空 Ledger；冲突可诊断 | 丢失 ID、关系或时间，偷偷合并不同历史、只校验 metadata |
| R07 | 重启后仍可读取确认提交；不确定提交有可核对的结果 | 超时一律报告未提交，或把进程退出测试等同真实掉电证明 |
| R08 | 库与 CLI 可脱离特定产品独立安装、测试与使用 | 运行时必须访问私有仓库、模型服务或开发者机器 |
| R09 | 如实声明支持范围、限制、版本和证据；支持后续独立实现 | SQLite 文件格式被当作通用替换协议，或以单实现往返宣称替换已证 |
| R10 | 后续一致快照恢复保留身份、版本、内容、来源与幂等结果 | 覆盖已有恢复目标、直接复制正在变化的数据库文件冒充一致快照 |

## 3. A1 范围与约束

A1 交付 Python 库、JSON CLI、三类写操作、精确读取/校验、整库可移植导出/导入及必要测试。具体接口和资源上限以 [接口提案](INTERFACE_PROFILE.md) 为唯一字段级定义；[架构](ARCHITECTURE.md) 规定一致性边界。

初期使用本地可靠文件系统、单一受信数据域、单写入者部署。元数据和有界 payload 同驻 SQLite；不让多台机器写同一 NAS 挂载数据库。数据量超出 profile 限制时明确失败，不截断历史或静默降级。

既有 ID 和历史不可覆盖；全局 ID 空间必须检查碰撞。输入被视为数据，工作流和脚本只存不执行。外部 refs 不触发联网查验，也不授予本组件管理外部对象的责任。普通内容校验不是来源认证。

本阶段没有网络服务、云同步、多租户权限、分布式写入、主动 erase/GC、向量检索、Ontology 推理、知识 Review、Agent Runtime、自我修改或节点编排。包含 `erased` 状态的导入属于当前 profile 不支持，不能恢复成可用字节。

| 阶段 | 必须产生的证据 | 当前状态 |

A1 通过后可以开始受限消费者试点，同时推进 A2。功能完成声明需同时检查真实恢复与 A3 两类消费者；跨实现替换需 A4，不能相互代替。知识应用的审核、知识退休和跨库恢复闭包由其自身项目负责，不扩大本 Ledger 的准入权限。

## 5. 待确认事项与风险

本提案建议最低 Python 3.11、MIT 许可、Linux/Python 3.11 必验组合和接口文档中的固定上限。首次实现无需为当前需求引入 3.12 专属 API；3.12 的附加验证不能代替 3.11 验收。Owner 确认文档时一并确认这些选择；A1 首次实现负责验证可行性。尚未发布软件，尚无性能或跨平台支持承诺。许可证文件在确认后加入，发布前必须存在。

SQLite/文件系统故障、内存峰值、可移植内容超限、调用方错误换 key、未来消费者要求变动是主要风险；[实施计划](IMPLEMENTATION_PLAN.md) 为每项关键不变量安排可定位验证。若验证推翻固定边界，应先修订文档并重新确认受影响范围，不以既成代码改变需求。
