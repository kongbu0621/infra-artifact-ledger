## PR13 再复核：wheel 与运行模块绑定

检查 `bf0475c` 时，实际复现了验收脚本的身份误判：先从 wheel A 比较模块，关闭后文件路径被替换为 B，随后从 B 计算摘要，原检查仍可通过。此外，字典收集 ZIP 成员会隐藏重复条目；只取文件名比较会忽略模块的相对路径。

[当前脚本](closure-probe.py)改为一次有界读取 wheel，从同一份内存内容核对预期 SHA-256 和模块字节。17 个 Python 模块必须无重复且与受核对目录的完整相对路径集合一致；整包上限 64 MiB、模块展开总量上限 16 MiB。随后路径被替换也不能把两个 wheel 的身份混在一个通过结果中。这里核对的是读取到的内容，不宣称路径之后永久不变或已加载的进程内存得到证明。

[可复跑检查](check-wheel-binding.py)的 12 项测试通过，覆盖正常包、替换时序、错误摘要、重复/错名/额外模块、同长内容变化、链接与非规范路径、子目录模块，以及上一轮的优化模式拒绝和旧证据保护。运行命令：

```sh
python3 -I -B docs/evidence/2026-10-17-a2-final-reconciliation/check-wheel-binding.py
```

另从保留的真实 wheel 核对原报告的全部 17 个模块摘要，与固定 Git 源 `d4ba0c6` 及当前源码一致；原最终验收 75 个归档条目、上一轮复核 15 个条目仍全部匹配原摘要。没有发现原报告绑定了另一版本的证据，配置内 A2 结论保持不变。当前脚本摘要、检查结果和具体限制见[本轮回执](wheel-review-receipt.json)；之前两份回执及原现场结果不改写。

身份检查之后的整段业务代码和 20 条业务断言保持原样。本轮只执行本地回归及保留材料只读核对，未再次完整运行验收脚本、重放 Ledger/NAS 业务或修改产品。复核控制器首次因误把 AST 遍历顺序当源码顺序而失败，修正为比较完整业务代码树后通过，失败留档。
